# لایسنس آفلاین پلاکینو

## راه‌اندازی یک‌باره نزد صادرکننده

وابستگی‌ها را با `uv sync` نصب کنید. سپس از ریشهٔ پروژه اجرا کنید:

```bash
uv run python scripts/issue_license.py keygen \
  --private /secure/plakino/issuer.private.pem \
  --public src/plakino_license/issuer_public.pem
```

مسیر `/secure/plakino` نمونه است؛ آن را با پوشهٔ امن و قابل‌نوشتن خودتان عوض کنید.
ابزار رمز عبور کلید خصوصی را دو بار می‌پرسد. فایل خصوصی با رمز ذخیره می‌شود؛ آن را
به‌همراه رمز در محل امن پشتیبان‌گیری کنید و هرگز برای مشتری نفرستید. فقط
`issuer_public.pem` باید همراه بستهٔ مشتری باشد. ابزار فایل موجود را بازنویسی نمی‌کند.
فعلاً کلید واقعی صادرکننده در این مخزن ساخته نشده است؛ برنامه بدون کلید عمومی
و لایسنس معتبر، پردازش را فعال نمی‌کند. یک کلید عمومی ثابت برای همهٔ نسخه‌های
متعلق به همان صادرکننده نگه دارید؛ تعویض آن لایسنس‌های قبلی را نامعتبر می‌کند.

امضا از نوع Ed25519 و با کتابخانهٔ cryptography انجام می‌شود:
[مستندات رسمی](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/).
ابزار خصوصی در `scripts/issue_license.py` است و جزو ماژول‌های بستهٔ مشتری نیست.

## گردش کار هر مشتری

۱. مشتری در نوار پردازش روی «لایسنس» می‌زند، پوشه را انتخاب می‌کند و
«ذخیره درخواست در این پوشه» را می‌زند. فایل `device-request-….json` را برای شما می‌فرستد.
این کار بک‌اند را بدون شروع پردازش بالا می‌آورد. شناسه‌های خام سخت‌افزار ارسال نمی‌شوند.

۲. روی سیستم خودتان یکی از فرمان‌های زیر را اجرا کنید:

```bash
uv run python scripts/issue_license.py issue \
  --private /secure/plakino/issuer.private.pem \
  --request device-request.json --days 15 --output customer.plakino

# برای ۳۰ روز از --days 30 و برای شش ماه تقویمی از --months 6 استفاده کنید.
```

اعتبار **از لحظهٔ صدور** شروع می‌شود، نه از نخستین ورود فایل. زمان‌ها timestamp
بر حسب UTC هستند؛ پنجرهٔ برنامه پایان اعتبار را به وقت تهران، با تاریخ میلادی نشان می‌دهد.
ماه تقویمی با حفظ ساعت و محدودکردن روز به آخر ماه مقصد محاسبه می‌شود.

۳. فقط فایل `customer.plakino` را برای مشتری بفرستید. مشتری آن را در همان پنجره
انتخاب می‌کند و «ورود فایل لایسنس» را می‌زند. ورود موفق، خودکار پردازش را شروع نمی‌کند؛
کاربر دکمهٔ «اجرا» را می‌زند. تمدید نیز با درخواست دستگاه و صدور فایل جدید انجام می‌شود.
ورود فایل نامعتبر، لایسنس معتبر فعلی را جایگزین نمی‌کند.

جایگزین خط فرمان برای مشتری (بدون نیاز به بازبودن UI):

```bash
uv run python -m plakino_license request device-request.json
uv run python -m plakino_license import customer.plakino
uv run python -m plakino_license status
```

## رفتار اجرایی و زمان

- بررسی در خود بک‌اند، پیش از بارگذاری و پس از بارگذاری مدل‌ها و هر پنج ثانیه
  هنگام اجرای میزبان انجام می‌شود؛ بسته‌بودن UI اثری روی آن ندارد.
- هنگام انقضا یا عقب‌رفتن ساعت، توقف عادی پردازش درخواست می‌شود؛ تخلیهٔ صف‌ها
  ممکن است زمان بیشتری ببرد. UI و میزبان کنترل برای تمدید باز می‌مانند.
- آخرین زمان معتبر، شناسهٔ لایسنس‌های منقضی و فایل فعال با نوشتن اتمیک و HMAC
  ذخیره می‌شوند. در طول عمر پردازه، زمان‌سنج monotonic نیز مانع کاهش زمان مؤثر می‌شود.
- عقب‌رفتن بیش از ۱۲۰ ثانیه پردازش را مسدود می‌کند؛ اصلاح کوچک ساعت هم زمان
  مؤثر را عقب نمی‌برد و به مدت اعتبار اضافه نمی‌کند. اصلاح ساعت به مقدار صحیح
  می‌تواند خطای ساعت را رفع کند؛ انقضای ثبت‌شده برای همان شناسه رفع نمی‌شود.
- پس از انقضا، فقط لایسنس جدید معتبر امکان ادامه می‌دهد. برگرداندن فایل قدیمی
  یا ساعت به عقب آن لایسنس را فعال نمی‌کند، تا وقتی سابقهٔ دستگاه باقی باشد.
- سابقهٔ ناقص، خراب یا غیرقابل‌نوشتن باعث رد اعتبار می‌شود. تاریخ نادرستِ خیلی
  جلو ممکن است لایسنس را برای همیشه منقضی ثبت کند؛ ساعت را پیش از فعال‌سازی بررسی کنید.

محل داده مستقل از فایل‌های برنامه است:
Linux: `~/.local/share/plakino/license`، Windows: `%LOCALAPPDATA%/plakino/license`.
فقط میزبان بک‌اند این داده‌ها را می‌نویسد؛ UI و CLI از کانال محلی احرازشده استفاده می‌کنند.
ارتقا نباید این پوشه را پاک کند. بک‌اند و UI باید با همان حساب کاربری نصب اجرا شوند؛
نصب به‌شکل سرویس با حساب متفاوت نیازمند تنظیم مسیر و مجوزهای مشترک در نصب‌کننده است.

## اتصال به دستگاه و محدودیت‌ها

Linux از machine-id و مشخصات موجود DMI، Windows از MachineGuid و UUID/سریال
مادربرد استفاده می‌کند. در Linux مدل/سازندهٔ مادربرد نیز خوانده می‌شود تا حساب عادی
بدون دسترسی به سریال بتواند درخواست بسازد. حداقل شناسهٔ نصب و یک مشخصهٔ سخت‌افزار
لازم است؛ در نبود آن‌ها درخواست رد می‌شود. ترکیب دقیق هش‌ها باید یکسان بماند؛ تعویض
مادربرد، نصب دوبارهٔ سیستم یا تغییر سطح دسترسی خواندن DMI ممکن است نیازمند صدور مجدد باشد.
این نسخه Linux و Windows را هدف می‌گیرد؛ آزمون اجرایی Windows هنوز انجام نشده است.
محیط توسعهٔ فعلی شناسه‌های کافی DMI در اختیار نمی‌گذارد؛ جمع‌آوری شناسه با داده‌های
آزمایشی بررسی شده و باید روی دستگاه واقعی مقصد نیز تأیید شود.

این حفاظت صددرصدی نیست: مدیر سیستم می‌تواند کد/کلید عمومی را عوض کند، کلید محلی
HMAC را استخراج کند، تمام داده‌ها را حذف کند یا بکاپ کامل سیستم را برگرداند.
ماشین مجازی کلون‌شده نیز ممکن است شناسه‌های یکسان داشته باشد. timestamp به‌خودی‌خود
منبع زمان قابل‌اعتماد نیست. تضمین قوی‌تر نیازمند ساعت امن یا بررسی آنلاین است.

پس از ارتقای این تغییر، میزبان بک‌اند قبلی را یک‌بار متوقف و دوباره راه‌اندازی کنید؛
صرف بستن UI نسخهٔ در حال اجرای بک‌اند را عوض نمی‌کند.
