مسیر ۳ / آزمایش مشترک تمام مرحله‌ها

خودروی ۴۲ از گیت ورودی عبور می‌کند.

این یک مثال آموزشی است، نه دادهٔ ثبت‌شدهٔ واقعی. فرض می‌کنیم cam-1 با گیت مستقل ثبت شده، برش موجود است، پلاک خوانده می‌شود و صف‌ها ظرفیت دارند. هر کارت را باز کن تا نقطهٔ دیباگ را ببینی.

۱فریم رهگیری‌شدهCameraTracker.process → TrackedFrame

هر فریم دوربین، شماره و زمان دارد؛ هر تشخیص می‌تواند track_id و bbox داشته باشد.

camera_id=cam-1, track_id=42, class_id=2

ابتدا camera_id، frame_idx و detections را ببین. نبود تشخیص را با نبود تصویر یکی نکن.

۲عبور و انتخاب تصویرline_worker + crop_worker

دو شاخهٔ فریم هم‌زمان جلو می‌روند. LineDetector رویداد عبور می‌سازد؛ selector برش مناسب را نگه می‌دارد.

direction=entry; event + best_crop

آیا cross_queue رویداد گرفته؟ آیا selector.get برای همان camera_id/track_id برش دارد؟

۳خواندن پلاکocr_worker → PlateReader.read

برای خودرو با برش، OCR اجرا می‌شود. پیام نهایی برای writer آماده می‌شود.

روی ورودی و خروجی read توقف کن؛ متن خالی، خطای OCR و پرشدن db_queue سه مسئلهٔ متفاوت‌اند.

۴ورود به writerdatabase_worker → _save_event

worker پیام می‌گیرد. _save_event ابتدا وجود خودرو، سپس رویداد و جلسه را مدیریت می‌کند.

item → event_id

item را پیش از SQL ببین. track_id هنوز در پیام هست ولی در ستون‌های INSERT نیست.

۵ثبت نهاییINSERT_EVENT → session → commit

برای ورود تازه جلسه باز می‌شود. commit تغییرات این پیام را نهایی می‌کند.

vehicle: 1 | event: 1 | open session: 1

شناسهٔ برگشتی را یادداشت کن. captured_at از NOW() می‌آید. SQLهای دیگر اتصال، دادهٔ commitنشده را معمولاً نمی‌بینند.

۶خواندن مستقلPlateService + DashboardService

داشبورد با اتصال‌های خواندن جدا، ردیف‌ها و شمارش‌ها را می‌گیرد.

۷بازگشت به UI_load → Clock.schedule_once → _apply

نتیجه از thread دریافت داده به چرخهٔ UI برمی‌گردد؛ نتیجهٔ قدیمی کنار گذاشته می‌شود.

حالا همان خودرو خارج می‌شود…

یک event خروج جدید ایجاد می‌شود. اگر جلسهٔ باز همان پلاک موجود باشد، UPDATE_CLOSE_SESSION شناسهٔ خروج و زمان بسته‌شدن را روی آن می‌گذارد. نتیجهٔ سناریوی عادی: یک vehicle، دو event و یک vehicle_session بسته. خروج بدون جلسه هم event دارد ولی هشدار ثبت می‌شود.

سه گذر پیشنهادی: ابتدا پیام آماده → DB (مرحلهٔ ۳)، سپس DB → UI (۵ تا ۷)، و در پایان تصویر → پیام (۹ تا ۱۱). این ترتیب بار یادگیری را کمتر می‌کند.

مهارت اصلی / پیدا کردن چرایی

برای هر تابع، این شش سؤال را جواب بده.

  1. چه کسی این تابع را اجرا می‌کند؟
  2. ورودی واقعی چه شکلی دارد؟ یک نمونه بنویس.
  3. چه تصمیم یا تبدیلی انجام می‌دهد؟
  4. چه چیزی برمی‌گرداند و چه چیزی را تغییر می‌دهد؟
  5. چرا مسئولیتش در این ماژول قرار گرفته؟
  6. اگر خراب شود، شاهدش در کدام متغیر، لاگ یا جدول است؟

مثال: _save_event

فراخواننده: worker. ورودی: cursor و item. تصمیم: رویداد پلاک‌دار است؟ ورود است یا خروج؟ جلسهٔ باز دارد؟ خروجی: event_id. اثر جانبی: SQLهای تراکنش جاری. دلیل جداسازی: قواعد تردد از حلقهٔ صف جدا هستند. نقطهٔ بررسی: item و open_session و دستورهای اجراشده؛ commit در فراخواننده است.

اولین دیباگ، بدون دوربین و PostgreSQL واقعی

تست writer از اتصال mock استفاده می‌کند. در ترمینال ریشهٔ پروژه فرمان زیر را اجرا کن. دستور اول دیباگر را باز می‌کند؛ سه خط بعد را در اعلان (Pdb) وارد کن:

PYTHONPATH=src .venv/bin/python -m pdb -m unittest computer_vision_v2.database.test_database_worker.DatabaseWorkerTests.test_event_with_plate_creates_vehicle_and_entry_session
b src/computer_vision_v2/database/database_worker.py:13
c
p item

با n به خط بعد برو، با s وارد تابع شو، با p open_session مقدار را ببین، با where فراخواننده‌ها را پیدا کن و با c اجازه بده تست تمام شود؛ بعد از پایان تست با q خارج شو. توقف اجباری وسط worker ممکن است تست را ناقص کند و خطای مصنوعی نشان بدهد. لازم نیست وارد داخلیات کتابخانهٔ mock شوی. برای متغیری که هنوز مقدار نگرفته، ابتدا به خط بعد از انتساب برس.

در ویرایشگر هم همین کار را با breakpoint روی اولین خط _save_event و اجرای تست در حالت Debug می‌توان انجام داد. هدف دیدن داده است، نه حفظ‌کردن فرمان‌ها.

آزمایش SQL واقعی؛ بعد از فهم mock

روی یک دیتابیس آزمایشیِ جدا با همین schema و یک دوربین/گیت معتبر کار کن. ابتدا با SELECT ردیف‌های مربوط به یک پلاک فرضی را ببین، سناریوی ورود/خروج را اجرا کن و دوباره همان SELECTها را بررسی کن. پیش از اجرای writer، مطمئن شو get_connection به همان دیتابیس آزمایشی وصل می‌شود. این راهنما اتصال را تغییر نمی‌دهد.

SELECT id, camera_id, plate_number, event_type, captured_at
FROM event ORDER BY id DESC LIMIT 10;

SELECT plate_number, status, entry_event_id, exit_event_id
FROM vehicle_session ORDER BY id DESC LIMIT 10;

قبولی: ورود پلاک تازه → خودرو + رویداد + جلسهٔ باز؛ خروج → رویداد جدید + همان جلسهٔ بسته؛ بدون پلاک → فقط رویداد. خطای محدودیت را در تراکنش آزمایشی بررسی کن و اثر rollback را ببین. mock ترتیب فراخوانی‌ها را بررسی می‌کند؛ این آزمایش محدودیت‌ها و SQL واقعی را.

مرجع کوچک کنار دستت

واژه‌ها را با همین پروژه یاد بگیر.

ماژول
یک فایل پایتونی با مسئولیت مشخص؛ با import از آن استفاده می‌کنیم.
تابع و متد
تابع کار مشخصی انجام می‌دهد؛ متد تابعی در کلاس است و معمولاً با self به وضعیت شیء دسترسی دارد.
مدل داده
شکل نام‌گذاری‌شدهٔ داده، مثل PlateRecord؛ لزوماً جدول دیتابیس یا مدل هوش مصنوعی نیست.
سرویس
بخشی که یک کار کاربردی مثل خواندن ترددها را برای بقیه انجام می‌دهد.
cursor
ابزار اجرای SQL و گرفتن ردیف‌ها روی یک اتصال.
تراکنش
چند تغییر مرتبط که commit آن‌ها را نهایی و rollback تغییرات نهایی‌نشده را لغو می‌کند.
صف و worker
صف پیام‌ها را نگه می‌دارد؛ worker آن‌ها را می‌گیرد و کار می‌کند.
thread
مسیر اجرای هم‌زمان داخل فرایند؛ صف‌ها محل تحویل کار بین این مسیرها هستند.
callback
تابعی که به بخش دیگری می‌دهیم تا هنگام یک رویداد یا در زمان بعدی اجرا کند.
mock
جایگزین کنترل‌شدهٔ یک وابستگی در تست؛ رفتار PostgreSQL واقعی را کامل اثبات نمی‌کند.
breakpoint
نقطهٔ توقف اجرا برای دیدن متغیرها و مسیر فراخوانی.
اثر جانبی
تغییر خارج از مقدار خروجی تابع: نوشتن دیتابیس، فایل، صف یا widget.

روش ادامه: یک مرحله → سه پاسخ و یک شاهد → بازخورد در چت → تصمیم برای مرحلهٔ بعد. برای شروع سریع، فقط مرحلهٔ ۱ را انجام بده.

این فایل راهنمای کد بررسی‌شده در ۳ اکتبر ۲۰۲۶ است. درخواست شبکه یا ارسال خودکار پاسخ ندارد. تیک‌ها و یادداشت‌ها در مرورگر ذخیره می‌شوند؛ برای انتقال یا پشتیبان، «دریافت یادداشت‌ها» را بزن. ذخیره‌سازی فایل‌های محلی در بعضی مرورگرها محدود است؛ در آن حالت پیام وضعیت را ببین.
